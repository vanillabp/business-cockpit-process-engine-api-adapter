# The extension depends on the extension SPI and no longer on the adapter SPI

**Status:** decided, 2026-11-21, story 2191, the follow-up of the same story of
`adapter-platform-integration` (its `DECISIONS.pending/2191.md`) and of `business-cockpit` (its
`DECISIONS.pending/2191.md`). No entry of this log is superseded. The entries which name
`BpmnTaskSpec` and `WorkflowTaskWiring#isClaimedByAWorkflowService` stay true: the adapter still
hands over a `BpmnTaskSpec`, and the bean is still the same. The extension reads both through the
narrow interfaces below.

The extension used to read five types from the core of VanillaBP and the adapter SPI:
`MigrationAdapterProperties` for the configured adapter ids and the root prefix,
`TaskDeliveryLogResolver` for the delivery log of a workflow aggregate, `BpmnTaskSpec` for the
names of a user task, and `WorkflowTaskWiring` for two questions about what the application
declared. None of them was a promise to an extension.

The platform now offers what an extension needs in its SPI artifacts, and the extension uses that:

- `VanillaBpSettings` of the extension SPI answers `adapterIdsOfType` and `PREFIX`. Both platform
  modules take it, and the Spring Boot auto-configuration waits for a bean of that type.
- `TaskDeliveryLogResolver` is an interface of the extension SPI now, package
  `io.vanillabp.integration.extension.spi.resolver`.
- `BpmnTaskElement` of the integration SPI is what `PeaCockpitObserver`, `PeaRecordedUserTasks` and
  `PeaUserTaskElements` read from a deployed process.
- `WorkflowTaskClaims` of the integration SPI answers `isClaimedByAWorkflowService` and
  `workflowsShareTheWorkflowAggregate`. `PeaCockpitObserver` takes it for the first question,
  `PeaBusinessCases` for the second, and the two platform modules hand it over.

The POMs follow. `migration-adapter` is a test dependency of the Quarkus runtime module only, for a
test which builds the configuration the way the platform binds it. The core module no longer
declares `vanillabp-adapter-spi`. It still arrives through the Process Engine API adapter, and the
tests use it to play the adapter. The Spring Boot module calls
`AdapterBeanRegistrarSupport#forEachConfiguredAdapterId` of the Spring Boot integration, which the
platform allows. It never declared that artifact, and it still takes it through the Process Engine
API adapter.

An enforcer rule `an-extension-depends-on-the-extension-spi-alone` in the root `pom.xml` bans
`migration-adapter`, `vanillabp-adapter-spi`, `vanillabp-spring-boot-integration` and
`vanillabp-quarkus-integration` in the scopes `compile`, `provided` and `runtime`. It is the rule of
`extensions-commons`, with one difference: it checks only what a module declares
(`searchTransitive=false`). The Process Engine API adapter is a BPMS adapter. Its modules depend on
the adapter SPI and on the platform integrations, on purpose. A transitive ban would ban the adapter
this extension plugs into, and excluding those artifacts would break the adapter at runtime. No
module takes an artifact out of the ban.

Referred to by: the root `pom.xml` (the enforcer rule), `AGENTS.md` (section "This
is an extension, not a BPMS adapter").
